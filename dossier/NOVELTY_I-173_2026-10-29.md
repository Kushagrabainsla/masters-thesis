# I-173 Measured fusion selection: novelty and adversarial check (R-61)

Date: 2026-10-29. Requested by the user ("Novelty check"). No GPU spend. Labels: FACT, INTERPRETATION, HYPOTHESIS.
Reviews: main-session pass 1 (this file, Sections 2 to 6) and a Sonnet adversarial pass 2 (Section 7).

## 1. One-sentence idea
Today vLLM turns each graph-level fusion on or off with a fixed rule. The idea: at compile and CUDA-graph capture time,
time each fusion on and off for each token range, and keep the faster choice.

Origin: O-03 / E-46. On 1 x H100, the block-FP8 norm+quant and SiLU+quant fusions make decode 2% to 6% slower when
they fire (deep_gemm and cutlass engines), and a fixed rule turns them on.

Research question (as first written): can measurement-driven, per-range fusion selection at startup beat vLLM's fixed
fusion rules on decode throughput, across GPUs, models and engines, without an accuracy change and with a startup cost
below a fixed limit? The answer is "no" if the best single fixed setting per (GPU, engine) gets nearly the same speed.

## 2. Problem reality (FACT)
- O-03 (E-44, E-46): two fusions are 2% to 6% slower when they fire on H100 with deep_gemm or cutlass.
- vllm-project/vllm#34391 (2026-02): the qknorm+rope fusion is slower than unfused on H100. Fixed in the kernel by
  PR #37376 (merged 2026-04-13, per-batch-size kernel configs for sm90), not by a selection mechanism.
- Correction after pass 2: pass 1 also cited vllm-project/vllm#55687 (8x slower rope fusions on gfx950). Its reporter
  retracted it on 2026-09-07 as a measurement artifact. It is not evidence.
- vLLM `docs/design/fusions.md` (lines 212 and 240) says "On NVIDIA, Inductor actually generates a faster fused kernel
  than our custom CUDA kernel", so the norm and SiLU quant fusions are on only when the custom op is in use. For
  block-FP8 the `quant_fp8` custom op is forced on, so the fusion fires; E-46 shows that this corner is slower.
- vLLM main (commit 482e473, 2026-10-29), `vllm/config/vllm.py` `enable_norm_fusion`: the norm fusion turns on when
  the `rms_norm` or `quant_fp8` custom op is on. The rule has no speed check.
- `vllm/config/compilation.py` has the comment "TODO(luka) better pass enabling system."

INTERPRETATION: fusion regressions occur, and upstream knows that the enable rules are weak. But each known case was
fixed by a kernel change or a rule change. The problem is real and small, and it is local to (GPU, engine) corners.

## 3. What prior work and shipping systems already do (FACT, checked in source or primary docs)

| Work | What it already does | What it does not do |
|---|---|---|
| PyTorch Inductor `register_custom_op_autotuning` / `autotune_custom_op` (`torch/_inductor/kernel/custom_op.py`, first commit 2025-10-31, PR #164212) | For a custom op, times alternative decompositions against the custom op itself (fallback), per token range (`dispatch_on`, split points), with `min_speedup_threshold` and `benchmark_with_cudagraphs`; inlines the winner so Inductor can fuse it | Single-output ops only; vLLM does not use it (no call in vLLM main) |
| Inductor `benchmark_fusion`, `benchmark_combo_kernel` (`torch/_inductor/config.py`) | Times fused against unfused Triton kernels in the scheduler and keeps a fusion only if it is faster | Does not see vLLM pattern-match passes that insert hand-written CUDA ops |
| vLLM pass manager (`PostGradPassManager`, `is_applicable_for_range`, `compile_ranges_endpoints`) | Compiles a separate graph per token range and turns a pass on or off per range | Thresholds are hand-set tables (allreduce fusion size per GPU and TP size; rope_kvcache 256 tokens); no timing |
| vLLM IR (RFC #32358; `docs/design/vllm_ir.md`) | Ops with several providers (including reserved "native" and "unfused"), static priority lists (`ir_op_priority`) | The doc lists autotuning as a "future feature", but the doc now opens with "Deprecated": IR is being removed, `ir_op_priority` goes in v0.34.0 (#63371, 2026-10-23). Correction after pass 2: pass 1 read this as a scoop path; it is not |
| Helion integration (vLLM RFC #32219, PR #29051) | Offline autotuning with one config per batch size, dispatch at CUDA-graph capture, for `silu_mul_fp8` and `rms_norm_fp8` | Kernel configs, not fused-against-unfused choice; batch-size dispatch not in the prototype yet |
| TensorRT-LLM `AllReduceRunner` (`_torch/custom_ops/torch_custom_ops.py`) | Autotunes per power-of-2 token bucket between fused allreduce+norm+quant kernels and NCCL plus separate norm and quant (`fallbackRunSubsequentOps`); ranks agree through `DistributedTuningStrategy.MERGE` | One op family (allreduce epilogues) |
| "Deep Kernel Fusion for Transformers" (arXiv 2602.11808); FlashInfer-Bench (arXiv 2601.00227) | A profiler-driven scheduler picks fused-kernel variants at startup in SGLang before graph capture; offline kernel benchmark and injection into SGLang and vLLM | Not checked in full text (pass 2 summary only) |
| vLLM RFC #42770 (open, 2026-05) and RFC #43224 | Plan: move compiler fusions into model code as "big fused ops" and later deprecate vLLM's torch.compile integration | Selection between a fused op and its unfused form at the call site is not specified |
| Kernel autotuning: FlashInfer autotuner (vLLM warmup, rank-0 cache broadcast), TensorRT-LLM `_torch/autotuner.py` (NVIDIA/TensorRT-LLM#8779), vLLM RFC #58751 | Time kernel tactics per shape bucket at warmup and cache the choice | Choose kernels, not graph rewrites |
| Korch (ASPLOS 2024, arXiv 2406.09465); TVM Ansor and MetaSchedule; FusionStitching; Welder | Choose fusion or kernel orchestration from measured or modelled costs | Not applied to vLLM's serving passes; general compiler result |

Known correctness risks of startup timing (FACT): vllm-project/vllm#61053 and #58636 (autotune choices differ across
TP ranks, so ranks run different code), #62820 (autotune changes temperature-0 tokens). vLLM already handles this for
FlashInfer with a rank-0 cache broadcast.

## 4. Adversarial pass 1 (main session)
- **Novelty attack.** Fails. The core mechanism (time a fused custom op against its unfused decomposition per token
  range and keep the winner) ships in PyTorch Inductor since 2025-10. Measured fusion choice is an old compiler result.
- **Adjacent-work attack.** Fails. vLLM already has per-range pass gating; only the thresholds are hand-set.
- **Combination attack.** Fails. "Inductor custom-op autotuning + vLLM compile ranges" is an integration, with no
  new coupling or systems constraint.
- **Simplicity attack.** Fails. A one-time default change (turn off the two fusions on sm90 for deep_gemm and cutlass)
  gets all of the measured gain. See the oracle below.
- **Oracle attack (FACT, from E-46 `summary.json`).** Per-range choice against the best single fixed setting:
  P1 and P2 (deep_gemm): "off" wins at every batch size, so the per-range gain is 0%. P3 (cutlass): "on" wins only at
  batch 1, by 0.19% (off ÷ on = 0.9981), inside the noise. So the per-range part of the mechanism adds about 0% in our
  data. The whole gain comes from a fixed rule being wrong for one (GPU, engine) pair, and a fixed fix removes it.
- **Scale attack.** Not decisive. Default users on the H100 default engine are not affected (the fusion does not
  fire there).
- **Correctness attack.** Real, but known. Per-range choice changes numerics across batch sizes (batch invariance),
  and noisy timing can give different choices across restarts or TP ranks. vLLM already uses rank-0 broadcast and
  caches for FlashInfer; this is engineering, not a new research problem.
- **Scoop-risk attack.** High, for a different reason than pass 1 gave. RFC #42770 plans to remove the
  compiler-fusion path that the idea depends on, and RFC #43224 maps the two E-46 passes to manual fusion (#43500,
  #43501). (Pass 1 also named the vLLM IR autotuning plan; pass 2 showed that IR is deprecated.)

Reviewer rejection (pass 1): "This is Inductor's range-based custom-op autotuning applied to vLLM's fused ops, on a
compiler path that vLLM plans to remove, and on the authors' own data a fixed flag gets all of the gain."

## 5. Narrower cores tried in pass 1

- **An upstream contribution: use Inductor custom-op autotuning for vLLM IR providers (fused against "unfused").**

## 7. Adversarial pass 2 (Sonnet, fresh searches and source clones of vLLM, TensorRT-LLM and SGLang)
Verdict: KILL as a thesis mechanism. Confidence in a public gap: low. The main session checked the two key corrections
(#55687 retracted; vLLM IR deprecated) and the `fusions.md` lines in the source before applying them.
- New prior art: TensorRT-LLM `AllReduceRunner` already ships measured fused-against-unfused selection per token
  bucket, with a rank-agreement rule. Helion integration targets the same two ops with per-batch-size configs. Two
  2026 papers (2602.11808, 2601.00227) do startup or offline selection of fused kernel variants for SGLang and vLLM.
- SGLang: it has a pass-manager scaffold (`is_applicable_for_shape`) but no concrete fusion pass; fusion is written by
  hand in layers. No measured fused-against-unfused choice.
- Correctness: the risks are real and open in vLLM (#61053, #58636, #62820; SGLang notes that per-bucket tactics break
  batch invariance). The known answers (rank-0 broadcast, cache, MERGE, an off switch under `VLLM_BATCH_INVARIANT`)
  already exist. This is engineering, not a research problem.
- Rejection sentence (pass 2): "This is per-range measured selection among fused and unfused implementations, which
  Inductor custom-op autotuning and TensorRT-LLM's AllReduceRunner already ship; it targets passes vLLM is deleting,
  and its only measured gain is captured by flipping two flags."
- Conditional core (MEASURE-FIRST, low prior): time whole captured-step variants per CUDA-graph size, to catch fusion
  interactions and cold-L2 effects that op-level autotuning misses. Test: the E-46 harness, 2 x 2 fusion settings at
  decode sizes 1, 8, 32, 128, 512 and prefill 2048, 8192, plus one fusion that the default engine reaches (allreduce
  with RMSNorm at TP 2), at least 5 restarts. GO only if a fused setting wins by 3% or more at one size and loses by 3%
  or more at another (both beyond 2x the restart SD), per-size choice beats the best fixed setting by 2% or more on a
  mixed trace, and choices are stable in 95% of restarts. Thresholds are heuristics.
- Ratings: publication potential LOW. Upstream value LOW as a selector; MEDIUM as a note that the block-FP8 fused
  kernels must be fixed before the #43500 and #43501 manual-fusion ports.

## 8. Final verdict (R-61)
KILL as a thesis direction. Confidence in a public gap: low. Both passes agree.
- Main reason: the mechanism ships (PyTorch Inductor custom-op autotuning, TensorRT-LLM AllReduceRunner), its host
  path in vLLM is being removed, and on our own data a fixed flag gets all of the gain (per-range oracle gain about 0%).
- Not run: the conditional MEASURE-FIRST core in Section 7. Its prior is low, because E-46 shows only losses for the
  fused path, with no crossover. Run it only if the user wants to spend about $6 to close the question formally.
- Keep: U-01 as the fix for O-03. Add to U-01 the point that the manual-fusion ports (#43500, #43501) should not
  carry over the slow block-FP8 kernels.
- What would reopen it: a measured crossover (a fusion that wins by 3% or more at some sizes and loses by 3% or more
  at others) on a configuration that default users reach, on a path that vLLM keeps.

Lesson: check whether the host code path has a future (open RFCs and deprecation banners) before a novelty search on
the mechanism. Pass 1 missed a deprecation banner because it read only the lines that matched a search.
