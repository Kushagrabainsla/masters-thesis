# R-20: Gap search on three seed topics (2026-10-16)

Asked by the user on 2026-10-16: read recent papers, find what is already tested, find research gaps for
three seed topics, test them against more papers, and repeat until gaps appear. The seed topics:

1. Threads versus processes: use processes at low traffic and threads at high traffic.
2. KV cache poisoning.
3. The noisy-neighbor problem for GPU workloads.

Method: the `research-gap-dossier` skill. Three search rounds in the main session (Opus), then one
different-model adversarial review (Sonnet, D-29). Ideas I-110 to I-119. Labels: FACT (primary page or
full text read), SNIPPET (search summary or abstract only), INTERPRETATION, HYPOTHESIS.

## 1. Result in one paragraph

All three seed topics are crowded in 2025 and 2026. Topic 1 is a pattern that many published systems
already use (load-adaptive mode switching). Topic 2 has an NDSS 2026 paper, a USENIX Security 2026 paper,
and more than ten 2025 to 2026 preprints. Topic 3 was killed in this repo before (I-10), and new work
covers MPS, MIG, PCIe and MPS fault isolation. One candidate survives as MEASURE-FIRST with a low prior:
I-118, a noisy neighbor that couples through the shared CPU-GPU module power budget on Grace superchips.
Two candidates are WEAK (I-116, and I-114 by the reviewer's vote only). None is thesis-strong yet.

## 3. Topic 1: threads versus processes

**What the idea maps to.** In ML serving, "process" means isolation (separate address space or CUDA
context, no fate-sharing, expensive sharing). "Thread" means a shared context (MPS, one process with
streams or green contexts, merged adapters, shared batches). The user's rule switches to sharing when
load is high.

**Already published (FACT unless marked).**
- dLoRA (OSDI 2024): merges and unmerges LoRA adapters at runtime by load. This is the user's rule for
  adapters.
- Aegaeon (SOSP 2025, SNIPPET from press): token-level pooling of many low-traffic models. 1,192 to 213
  GPUs in Alibaba's beta.
- D-STACK (2304.13541) and GSLICE: MPS reconfiguration needs a new process; a standby process takes over.
- HAS-GPU (2505.01968, SNIPPET): MPS SM shares are fixed at context creation, so it uses time tokens.
- PD-multiplexing with green contexts (2504.14489, LMSYS blog) and LithOS (2504.15465, SOSP 2025): SM or
  TPC partitions that change at runtime, inside one process or transparently.
- Flying Serving (2602.22593) and ReMP (2606.18741): online switching between DP and TP.
- 2605.26461 (abstract, FACT): MPS fault isolation in the open driver and recovery in 355 ms. This
  removes the main cost of the shared ("thread") mode.

**Why the coupling is weak (INTERPRETATION).** Isolation needs come from trust and fault domains. They do
not fall when load rises. A system that drops isolation at high load gives an attacker or a faulty
client more power exactly when more users are exposed.

**Verdicts.** I-110 (GPU sharing mode) KILL. I-111 (Python front end under free-threaded 3.14t) KILL as
engineering: vLLM already has an in-process mode, and the remaining question is a benchmark.

## 4. Topic 2: KV cache poisoning

**Already published.**

| Work | What it shows | Check |
|---|---|---|
| "Cache Me, Catch You", NDSS 2026 | Six attacks: prefix-cache hash collisions (Python `hash` is reversible), semantic-cache fuzzy poisoning, block-wise and multimodal collisions. Five defenses; vLLM, GPTCache and AIBrix adopted fixes | partial full-text (abstract and searched PDF text) |
| HijackKV 2607.19957, USENIX Security 2026 | Position-independent reuse (CacheBlend, EPIC): a chunk's KV can encode an attacker prefix. About 94% single-try success; 39% left at 50% recompute; RobustKV fails; adaptive attack beats recompute. Recompute defense costs 1.00x to 3.53x. A deviation verifier is proposed but not evaluated | FACT (HTML) |
| Bit-flip KV 2604.17249, SECRYPT 2026 | Shared prefix blocks have one copy and no integrity check; a checksum at scheduling time bounds damage to one batch | FACT (abstract) |
| CacheTrap 2511.22681 | One KV bit flip as a Trojan trigger | SNIPPET |
| 2606.28958 | Tampered KV in multi-agent latent collaboration; HMAC manifest rejects 295 of 295 tampered payloads | FACT (abstract) |
| 2610.15721 (2026-10-11) | Cross-model KV reuse changes safety; value reuse is worse than key reuse; VReparo | FACT (abstract) |
| PrefixShield 2608.01657 | Cache pollution by one tenant; debt-based admission in vLLM | FACT (abstract) |
| KVGov 2608.09225, SafeKV 2508.08438, PromptPeek (NDSS 2025), 2409.20002 | Timing side channels and defenses (per-principal salts, selective sharing) | FACT (abstract) for KVGov |
| 2609.06853 | Contention cuts side-channel effect size (Cohen's d 0.78 to 0.21 on GB10) | FACT (abstract) |
| LMCache #5507, #3301; a CVE reported 2026-10-07 | Unauthenticated KV server, 16-bit multimodal hash | SNIPPET |

**Candidates.**
- **I-112 Cross-tenant prefix-cache pollution.** KILL. PrefixShield, CacheCast, 2608.14561, 2609.18112.
- **I-113 Integrity of KV in shared external stores.** KILL as research. Authentication (HMAC, as in
  2606.28958) and wider hashes are engineering fixes.
- **I-114 Sampled-recompute verifier for position-independent reuse.** KILL (main session), WEAK
  (reviewer). Main-session argument: re-encode each chunk alone (canonical context) before it goes into a
  shared cache. Then no attacker prefix enters the stored KV. This costs one chunk-only prefill per
  unique chunk, which a reuse factor R amortizes to 1/R per use, and it can run off the critical path.
  The HijackKV authors also say precomputed trusted chunks remove the attack path. The reviewer's
  dissent: the cost of re-encode for very large chunk stores is not measured. Reopen if a real
  deployment must publish chunk KV captured from user requests with a reuse factor near 1.
- **I-115 Eviction-steering attack on KV compression.** KILL. The benign version is published ("The
  Pitfalls of KV Cache Compression", ACL 2026; 2605.18053). Pinning instruction tokens defeats the
  adversarial version, and production engines do not evict by attention score by default.
- **I-119 Contention as a side-channel defense.** KILL. 2609.06853 measures it; salts already remove the
  channel.

## 5. Topic 3: noisy neighbor on GPUs

**Already published.** I-10 (this repo, KILL), 2508.20274 (PCIe-aware placement and MIG control),
2604.22430 (MPS versus MIG), 2601.07600 (MPS, MIG, green contexts on A100 and Orin), Hummingbird
2601.04071, Roomie 2607.16784, LithOS, 2603.22774 (CPU-induced slowdowns in multi-GPU inference),
2605.26461 (MPS fault blast radius). I-117 KILL.

**I-116 Per-tenant I/O QoS for KV storage tiers (mClock transfer).** WEAK. Neither search found
per-tenant reservation or limit scheduling for KV fetch bandwidth. CacheCast (placement with per-tenant
QoS), MTDS, ShadowServe 2509.16857 and EVICPRESS 2512.14946 (lists multi-tenant isolation as future
work) are adjacent. The premise is not measured. Cheap kill (reviewer): two clients on one NVMe-backed
KV tier; KILL if the victim's fetch latency rises by less than 20%.

### 5.1 I-118 Power-coupled noisy neighbor on CPU-GPU superchips

Status: MEASURE-FIRST. Confidence in gap: low.

**Problem.** On GH200 and GB200, the Grace CPU and the GPU share one module power limit. CPU-side work
on the same module can lower the power left for the GPU.

**Facts.**
- NVIDIA Grace tuning guide (FACT): module-scope capping monitors Grace power, removes it from the module
  limit, and gives the remainder to the GPU. For GB200, the GPU target is the lower of the programmed TGP
  and half of (module limit minus CPU power). The sample shows a 1000 W module limit (range 200 to 1000 W).
- HPE CUG 2024 slides (SNIPPET): the GPU manages module power, the CPU has preference, and the GPU is
  capped dynamically.
- 2605.01938, Section II-A (FACT, HTML): JUPITER limits GH200 to about 680 W; the CPU has priority by
  default; the default CPU cap is 100 W, to avoid GPU starvation. Measured CPU power during optimizer
  offload was 55 to 71 W.
- TU Dresden, ISPDC 2026 (SNIPPET, abstract): some GH200 power budgets are not enforced; decode dominates
  inference energy.
- 2605.11999 (SNIPPET): memory-bound decode on H200 draws 137 to 300 W and does not trigger caps.

**Why now.** Agent serving puts CPU work next to the GPU: tool sandboxes, tokenization, CPU KV offload and
compression, CPU attention offload, SuperOffload-style optimizer steps. On a superchip this work shares
the GPU's power budget. On a PCIe server it does not.

**Exact surviving gap.** I did not find a public measurement of how much CPU load on Grace slows GPU
prefill or decode through power steering. I also did not find a phase-aware CPU-GPU power split for LLM
serving on superchips. Do not claim the steering mechanism, power capping, or phase-aware GPU clocks as
new (Patrou 2505.21758, 2609.11133, GreenLLM 2508.16449, POLCA 2308.12908, Harmonia ISCA 2015 for APUs).

**Research question.** Under a binding module limit, does CPU-side co-located work lower GPU prefill
throughput by a meaningful amount, and does a phase-aware CPU cap beat the best static CPU cap?

**Hostile reviewer (Sonnet, R-20).** "This is a vendor power-steering knob that a static CPU cap already
handles. The effect appears only when an operator lowers the module limit, and the paper shows a
measurement without a mechanism that beats the one-line baseline."

**Power budget estimate (INTERPRETATION, not measured).** H100-class prefill draws about 600 to 700 W.
Grace under all-core load draws an estimated 150 to 250 W. The sum reaches 850 to 1000 W, so the default
1000 W limit binds only near full CPU load plus compute-bound prefill. The 680 W JUPITER limit binds
often.

**Premise test (E-30, not run, predeclared draft).**
- Setup: 1 x GH200, about 2 hours. First ask the provider whether the tenant has root, can read module
  power, and can lower the module cap (`nvidia-smi -pl X -sc 1`) and the CPU cap (hwmon `power1_cap`).
- Workload: vLLM, an 8B model, prefill-heavy requests (4K input, 16 output) and decode-heavy requests.
  Pin vLLM to reserved Grace cores. Load: `stress-ng --cpu` on 0, 18, 36 and 54 other cores.
- Control: a pure CUDA GEMM loop with no CPU work, to separate power coupling from CPU scheduling.
- Log: SM clock, GPU power, module power, Grace power, `clocks_event_reasons`.
- Limits: the provider default, and 680 W if the tenant can lower it.
- KILL 1 (heuristic): prefill throughput changes by less than 3% at both limits.
- KILL 2 (heuristic, from the reviewer): the best static CPU cap is within 5% of an offline oracle.
- PIVOT: the effect is real only at limits below any documented deployment; write a measurement note.
- GO (heuristic): at least 10% prefill loss at a documented limit, and an oracle gap above 5% over the
  best static cap.

**Likely output.** INTERPRETATION: a workshop measurement note is the realistic result, not a thesis core.
The reviewer predicts an oracle gain under 5% over a static cap.

**Unconfirmed lead.** The reviewer reported a DGX Spark (GB10) forum post that showed the GPU clock falling
while a CPU job ran. I searched and did not find it. Forum posts confirm that GB10 has a combined CPU-GPU
limit (about 140 W). Do not cite the anecdote.

## 7. Lesson

The R-10 to R-19 lesson holds again: in 2026, gaps found by literature search have early work within
weeks. The one survivor comes from a hardware change (a shared CPU-GPU power budget), not from a paper.
Ask the cloud provider about root and power telemetry before paying for E-30.
