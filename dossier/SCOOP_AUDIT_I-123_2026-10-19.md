# R-28: I-123 scoop audit and recovery-cut pivot

Date: 2026-10-19

Scope: I-123, current full-duplex serving, inference checkpointing, world-model migration, and stream-processing recovery.

## Verdict

PIVOT I-123. Do not run its old CPU oracle.

Create I-132 as a narrower candidate. I-132 studies one durable recovery epoch across model state and duplex protocol state.

Confidence that the public gap exists: low to medium.

Scoop risk: high.

## Why the old oracle is invalid

FACT: WorldMove measures one Matrix-Game 2.0 block at 375.6 ms. Its movable state is 1.67 GB.

FACT: WorldMove measures a 71% to 78% dirty fraction and a 0.93 GB/s dirty rate.

FACT: WorldMove reports a 96.4 ms to 101 ms warm install. It reports an 18.8 ms same-node move.

INTERPRETATION: A 200 ms recovery target cannot replay one 375.6 ms world-model block.

INTERPRETATION: Periodic snapshot plus input replay reduces to per-block state protection for this target.

FACT: The 200 ms target in I-123 was a project heuristic. It was not a workload standard.

FACT: Public speech systems do not give enough state-size data for the old parameter sweep.

INTERPRETATION: An algebraic sweep would encode its result through chosen constants.

## Narrow surviving question

Current systems expose separate pieces of the required recovery cut.

- A model checkpoint identifies a model-state epoch.
- An input ledger identifies accepted client input.
- A server-event journal identifies emitted output.
- A playback acknowledgement identifies output that the user consumed.

I did not find a public system that durably commits these four positions as one crash-recovery epoch.

The claim is not exactly-once network delivery. That claim is impossible without client participation.

The proposed contract uses stable event identifiers and client deduplication. Network delivery remains at least once.

## Two-pass review

### Pass 1: field map

Pass 1 mapped model-state capture, KV recovery, full-duplex session state, world-model migration, and stream recovery.

The closest works were Execution-State Capsules, WorldMove, Concordia, GhostServe, DejaVu, and vLLM-Omni.

### Pass 2: narrowed attack

Pass 2 searched engine-crash recovery, duplex checkpointing, event-sequence recovery, input logging, and acknowledged-output frontiers.

It also checked vLLM-Omni RFC 8429 and pull request 8485 from October 2026.

No direct public implementation appeared in these searches.

This absence is not proof of novelty.

## Novelty attacks

### Exact-work attack

No checked work joins a complete heterogeneous model snapshot with durable duplex input, output, and playback frontiers.

Concordia is the closest checkpoint mechanism. vLLM-Omni is the closest protocol mechanism.

### Different-name attack

Stream processors call the core idea a consistent checkpoint with a replayable source and transactional sink.

The paper cannot claim this protocol pattern as new.

### Adjacent-domain attack

Flink already gives exactly-once state updates. It needs a replayable source and a transactional or idempotent sink.

The research value must come from the accelerator and media-session constraints.

### Combination attack

The largest risk is a simple combination of Concordia, Flink, and vLLM-Omni.

I-132 survives only if one recovery epoch exposes a new cross-layer invariant or measurable trade-off.

### Baseline attack

The strongest simple baselines are full state replication for every unit and replay from the session start.

Both baselines can be correct with stable event identifiers and client deduplication.

### Oracle attack

The old oracle is killed. Sourced world-model values already determine its answer.

The replacement gate tests crash correctness before performance.

### Relevance attack

vLLM-Omni stores the whole duplex session in one engine-owned object. An engine loss therefore loses the session.

Its current reconnect path assumes that the engine session survives.

### Feasibility attack

A Mac Docker test can validate the recovery protocol with real process termination and durable storage.

It cannot validate GPU snapshot cost, cross-GPU determinism, or a production recovery objective.

### Scoop-risk attack

vLLM-Omni names replica-loss recovery as future work. It is also adding input acknowledgements now.

Concordia already supplies durable accelerator-state epochs. Scoop risk is high.

## New candidate

### I-132 Crash-consistent duplex recovery epoch

Conventional assumption: Model-state recovery and Realtime session recovery can be designed separately.

Possible truth: A valid recovery point must join the model snapshot and every externally visible session frontier.

Problem: A crash can restore valid model bytes but still duplicate audio, omit input, or corrupt conversation history.

Research question: Can one durable epoch recover model and protocol state without duplicate visible events under fail-stop crashes?

Constraint: The mechanism must add less than one application unit of latency under a supported workload.

Hypothesis: A committed epoch plus stable event identifiers can pass all crash cuts with bounded replay.

Negative result: Kill the idea if a simple full-copy or replay baseline meets the same objective.

## Cheapest experiment

Use E-34 only as a screen.

Run a deterministic opaque-state service inside Docker. Terminate its worker at every durable-operation boundary.

Use an external client that persists received event identifiers. Compare recovery with an independent reference execution.

Test three correct policies.

1. Replay the complete durable input log.
2. Persist a complete state snapshot after every application unit.
3. Persist periodic state snapshots plus input and output logs under one epoch.

Use negative controls only to validate fault injection. Do not use deliberately incorrect controls as baselines.

## Predeclared decision

These thresholds are project heuristics.

KILL-NOVELTY: Kill I-132 before implementation if the independent review finds only a standard checkpoint protocol.

KILL-CORRECTNESS: Kill the mechanism if it fails one legal crash cut after the protocol is frozen.

KILL-SIMPLE: Kill it if full per-unit state protection meets the same recovery objective within 3% steady-state overhead.

KILL-REPLAY: Kill it if full replay meets one application-unit recovery for the supported workload.

PIVOT-GPU: Keep only a GPU feasibility study if the protocol passes but Docker performance has no external validity.

GO-GPU: Proceed only if both simple baselines fail and the protocol passes every crash cut.
