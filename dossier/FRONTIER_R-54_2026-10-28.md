# 4. Surviving ideas (both WEAK)

## 4.1 I-165: Version-exact rollout lifecycle (from C2)
- Secret: RL frameworks treat "pause, update, resume" as safe, but in-flight tokens and kept KV can mix policy
  versions without any record. The mix is deliberate in some systems and accidental in others.
- Problem: the training signal assumes a behavior policy. Mixed-version tokens make that policy unknown unless
  every token is tagged.
- Closest prior work: DORA (single version per trajectory), PipelineRL and Motif 3 (deliberate mixing with
  importance-sampling correction), ROLLART (rebuild KV), vLLM #48311 (lifecycle contract, no version field).
- What prior work solves: version tagging per trajectory (DORA, Motif 3); staleness bounds; KV rebuild.
- Exact remaining question (narrow): I did not find public work that (a) states a per-token version invariant
  for engine lifecycle transitions, (b) checks it in vLLM, SGLang and verl, and (c) measures the cost of
  enforcing it with an epoch scheme (RCU-style grace periods for KV blocks) against keep-stale-KV.
- Research question: Can epoch-tagged KV with grace-period reclamation enforce "each token under exactly one
  declared policy version" at a throughput cost below a full KV rebuild, on dense and MoE models on one
  8 x H100 node?
- Hypothesis: today's default paths violate the invariant on some transitions; an epoch scheme costs much less
  than a rebuild.
- Strongest baseline: DORA-style per-version instances; full KV rebuild (ROLLART, MiMo); keep-stale-KV with
  per-token tags (Motif 3).
- Kill condition: two or more major frameworks already enforce or check the invariant; or the epoch scheme is
  not cheaper than a rebuild by a meaningful margin; or violations never occur.
- Biggest novelty threat: vLLM maintainers own #48311 and #48312 and may define the version field first.
- Publication potential: LOW to MEDIUM (a correctness checker plus a mechanism; a workshop or an
  industry-track paper is more likely than OSDI). Open-source value: HIGH (vLLM, verl contribution).
- Product: a "rollout correctness" checker for RL platforms. Weak as a company; good as a career artifact.
- Confidence that the public gap exists: LOW.

## 4.2 I-166: Engine choice for MoE EP AlltoAll on one node (from C1, I-18)
- Secret: for MoE inference, copy-engine AlltoAll may beat SM AlltoAll at decode sizes, and the winner may flip
  between prefill and decode.
- Closest prior work: PyTorch CE AllGather flag (2.12), VCCL, T-CCL (2610.07098), NCCLX, ParallelKittens.
- Exact remaining question: I did not find a source on CE AlltoAll for EP inference dispatch and combine.
- Hostile rejection: "a per-layer boolean picked by a one-time profile; a tuning table, not a mechanism".
- Kill condition: gap under 2% (heuristic) against the best static choice, or CE never better.
- Publication potential: LOW. Confidence in the gap: LOW.

# 7. Exact first experiment (premise check for I-165, no GPU)
- Inputs: source of vLLM (main), SGLang, verl, slime, AReaL, OpenRLHF, PipelineRL at current commits.
- Procedure: for each framework, trace the weight-update path with in-flight requests. Record: (1) is generation
  paused, aborted or kept; (2) is KV kept, flushed or rebuilt; (3) is a policy version stored per trajectory, per
  request or per token; (4) is there a check that a token's logprob comes from the declared version.
- Output: `experiments/rollout_version_audit/audit.md` (one table row per framework, with file and line links).
- GO (heuristic): at least 3 frameworks keep in-flight requests or KV across an update without per-token
  version records or a check. Then a 1-GPU fault-injection test (small model, weight update mid-decode) to
  count mixed-version tokens, then the epoch-scheme design.
- PIVOT: frameworks record versions but none measure the cost of exactness; then the contribution is the cost
  measurement only (weaker).
- KILL: 2 or more frameworks already enforce a per-token or per-trajectory single-version invariant with a check,
  or vLLM #48311 adds a version field in the meantime.
- Rubber duck and a different-model review before any GPU run (D-29).
