# Frontier Systems Review R-21

Date: 2026-10-17

Scope: AI infrastructure, ML systems, LLM inference, agent systems, recovery,
scheduling, verification, and coupled CPU-GPU systems.

Status: literature review and experiment design. No thesis direction is chosen.

## Method and limits

This review used two literature passes.

Pass 1 mapped workload transitions and current systems. It covered about 50 search
queries. It included papers, official documentation, repositories, issues, and RFCs.

Pass 2 used narrower names for each candidate. It searched for exact mechanisms,
adjacent systems, simple baselines, and work from the last three months.

The review read the relevant parts of the closest sources. It did not reproduce GPU
results. The repo has no NVIDIA GPU in this session.

Novelty statements use this form: I did not find public work that answers the narrow
question. This statement is not proof that the work does not exist.

# 1. What changed in the world?

## 1.1 Agent execution became a coupled CPU-GPU workflow

**FACT.** MARS models agent execution as alternating GPU inference and CPU tool work.
It reports up to 5.94 times lower end-to-end latency. Its OpenHands integration reports
up to 1.87 times faster task completion.

**FACT.** SAGA treats the workflow as the scheduling unit. On 64 GPUs, it reports 1.64
times lower task completion time than vLLM with prefix caching and affinity routing.
It also reports 1.22 times higher GPU memory use efficiency and 99.2% SLO attainment.

**INTERPRETATION.** The request-level scheduling assumption is broken. This fact is no
longer a sufficient thesis gap by itself.

## 1.2 Agent state now spans more than the transcript

**FACT.** Crab reports that more than 75% of agent turns produce no recovery-relevant
OS state. It improves recovery correctness from 8% for chat-only recovery to 100%.
It cuts checkpoint traffic by up to 87% and stays within 1.9% of fault-free time.

**FACT.** Resume Means Resume tests five workflow frameworks. No two tested frameworks
have the same conformance profile. Its TLA+ model checks 7.4 million states.

**FACT.** Atomix adds epoch-tagged transactions and progress frontiers for tool effects.
It covers speculation, retries, contention, and external effects.

**INTERPRETATION.** Cross-layer recovery is important. The broad problem already has
several direct systems and contracts.

## 1.3 KV cache became distributed execution state

**FACT.** LMCache turns KV cache into shared storage and communication state. It reports
up to 15 times higher throughput when combined with vLLM.

**FACT.** Mooncake reports that an early metadata design could overwrite active blocks
during a rolling update. The result could corrupt ongoing inference.

**FACT.** A 2026 Mooncake RFC measured partial logical groups under object eviction.
The bad live-byte ratio falls to about 1% at 64 GB and above in its tested workload.

**FACT.** vLLM issue 49250 reports deterministic wrong output after a rejected KV load.
Two requests that share blocks can race during recomputation.

**INTERPRETATION.** A remote KV miss is not always a performance event. A partial load
or stale ownership decision can become a correctness event.

## 1.4 Code generation increased faster than verification capacity

**FACT.** Chen and Stratton study 300 million work events from 725,938 workers at 718
firms. The data cover January 2021 through March 2026.

**FACT.** After agent adoption, lines increased 30%, commits increased 20%, and pull
requests increased 23%. Resolved issues and epics did not increase significantly.

**FACT.** Pull-request review time increased 49%. Change requests nearly doubled.
Comments per pull request increased 35%.

The paper uses proprietary Jellyfish data and a staggered difference-in-differences
design. It is a working paper, not a peer-reviewed systems study. The paper received
funding from Stripe, Harvard, and Schmidt Sciences. Jellyfish checked disclosure only.

The paper also surveyed 100 Prolific engineers to validate time-use estimates. That
small convenience sample is supporting evidence, not the main result.

**FACT.** An ICSE 2026 study found that 7.8% of plausible SWE-bench patches fail when
all developer tests run. It found behavioral differences for 29.6% of plausible patches.

**FACT.** TestGRAD now optimizes tests to separate four candidate patches. It reports
84.2% Pass@1, which is 3.6 percentage points above its strongest reported baseline.

**INTERPRETATION.** Verification is a real bottleneck. Test generation and patch
selection are already crowded. A new thesis needs a different systems constraint.

## 1.5 Kernel supply and backend diversity increased

**FACT.** FlashInfer-Bench links kernel generation, correctness checks, performance
tests, and deployment. Its `apply()` mechanism can substitute kernels in vLLM and SGLang.

**FACT.** FlashInfer v0.7 selects different configurations for eager execution and CUDA
Graph replay. It persists results by hardware, software, policy, operation, and shape.

**FACT.** KernelBench-Verified changes the best reported geometric mean speedup from
1.43 times to 0.88 times under stronger tests and a realistic baseline. It also finds
that 28% of kernels from the best model increase peak GPU memory.

**FACT.** The vLLM consistency stack removes several shape-dependent kernel branches.
It accepts throughput costs to preserve one reduction order across training and rollout.

**INTERPRETATION.** Fast kernel generation makes qualification more important. However,
correctness-gated substitution and static consistent kernels now exist.

## 1.6 CPU and GPU power became coupled on superchips

**FACT.** NVIDIA documents automatic power steering on Grace Hopper and Grace Blackwell.
The GPU receives the module budget that remains after Grace CPU power.

**FACT.** NVIDIA documents a CPU cap as a way to provide more power to the GPU.

**INTERPRETATION.** CPU-side agent work can affect GPU service through power, not only
through memory and CPU contention. The size of this effect for LLM serving is unknown.

# 3. Ideas killed by prior work

## 3.1 Workflow-level agent scheduling

**Exact-work attack.** SAGA uses workflow execution graphs, session affinity, work
stealing, workflow-aware KV retention, and agent-level fairness.

**Different-name attack.** MARS calls the same transition heterogeneous co-scheduling.
It coordinates GPU inference and CPU tools through one control plane.

**Verdict.** KILL. A new scheduler must expose a narrower resource or correctness
constraint that SAGA and MARS omit.

## 3.2 Agent sandbox prewarming and joint resource admission

**Exact-work attack.** SpecBox predicts tool intent during token generation. It overlaps
sandbox startup with inference.

**Adjacent-domain attack.** Serverless systems already study prewarming, remote fork,
and workflow resource placement.

**Verdict.** KILL. This route is a direct serverless transfer with current agent work.

## 3.3 General cross-layer agent checkpoint and rollback

**Exact-work attack.** Crab selects checkpoints from OS-visible effects. DeltaBox adds
incremental process and filesystem checkpoints.

**Different-name attack.** Atomix handles external effects as transactions. Resume Means
Resume supplies a formal persistence contract and a reference sequencer.

**Verdict.** KILL. A system that combines these layers would be integration work unless
it exposes a new invariant.

## 3.4 Verification-aware scheduling for coding-agent fleets

**Relevance attack.** Chen and Stratton support the verification bottleneck. The study
does not show that test execution compute is the binding resource.

**Exact-work attack.** TestGRAD allocates iterative test work to separate candidate
patches. PatchDiff generates tests that distinguish patches.

**Adjacent-domain attack.** CI test selection and prioritization are mature. Microsoft
reports 15% to 30% compute savings while finding more than 99% of buggy pull requests.

**Combination attack.** A queue that combines CI prioritization with coding agents is
Paper A plus Paper B. It lacks a new constraint.

**Verdict.** KILL I-121. Reopen only with a public trace that shows a new coupling between
agent generation and scarce verification hardware.

## 3.5 Broad mid-decode inference checkpointing

**Exact-work attack.** FailSafe handles tensor-parallel serving failures. GhostServe
targets checkpointing for fault-tolerant LLM serving.

**Baseline attack.** KV offload, recomputation, and request retry are strong baselines.

**Verdict.** KILL as a broad direction. A new result must isolate an unsupported state
or failure model.

# 4. Surviving ideas

## 4.1 I-23 SafeDispatch, narrowed again

**Secret.** The fastest numerically valid kernel is not always the fastest kernel that
preserves an explicit model-output contract.

**Problem.** Current autotuners rank valid kernels by latency. Fixed tensor tolerances can
accept substitutions that change greedy tokens or model behavior.

**Evidence.** Integer Alibi finds cross-kernel differences of at most one BF16 spacing
under real INT8 scales. Earlier end-to-end results show that small local differences can
change sequences. FlashInfer states that the best configuration changes with the model,
precision, GPU, and serving mode.

**Closest prior work.** FlashInfer-Bench, FlashInfer v0.7, Integer Alibi,
KernelBench-Verified, and the vLLM training-inference consistency stack.

**What prior work already solves.** It solves kernel discovery, hidden correctness tests,
performance ranking, deployment substitution, and fixed-order consistent execution.

**Exact remaining question.** Does an end-to-end output contract change backend selection
often enough to provide more than a per-shape numeric allow-list?

**Research question.** Can output-aware qualification improve throughput by at least 5%
over the best static safe policy on two models, with no held-out contract violations?

**Hypothesis.** Block-scaled FP8 and fused MoE cells contain regime-dependent choices.
The fastest safe choice changes with batch size, routing skew, and graph mode.

**Strongest baseline.** FlashInfer autotuning with its reference checks, followed by a
per-shape allow-list. Also compare with one fixed deterministic backend.

**Cheapest experiment.** Run the oracle matrix in Section 7 on one H100. Add B200 NVFP4
only after the Hopper result passes.

**Kill condition.** Kill the dispatch thesis if oracle gain is below 2% on every model
and unsafe substitutions are below 2%.

**Biggest novelty threat.** FlashInfer-Bench already performs correctness-gated dynamic
substitution. The vLLM consistency stack already selects a fixed safe kernel set.

**Publication potential.** MEDIUM if the oracle passes on two models. LOW if the output
contract only changes labels and not the selected backend.

**Product opportunity.** Add a release gate for generated and experimental kernels.
Sell reproducible qualification evidence to inference operators.

**Confidence that the public gap exists.** LOW to MEDIUM. The narrow question remains
open in the checked work. The surrounding system is crowded.

## 4.2 I-120 Atomic activation for remote KV recovery

**Secret.** A remote KV hit must remain invisible until all required cache components and
ownership transitions commit at the scheduler boundary.

**Problem.** Current stores can provide object correctness while the runtime exposes a
partial or stale logical cache entry. Shared blocks, aborts, and asynchronous completion
can then produce wrong output, a crash, or an unbounded wait.

**Evidence.** vLLM issue 49250 shows deterministic wrong output after a rejected load.
LMCache issue 3207 shows a CUDA crash after a partial retrieve. LMCache issue 4155 shows
a process crash and a request that waits for more than 12 minutes.

**Closest prior work.** Mooncake Store, Mooncake RFC 3692, Fail-Closed Lowering, LMCache,
and the vLLM KV load recovery path.

**What prior work already solves.** Mooncake supplies immutable object reads and transfer
failover. RFC 3692 proposes non-visible uploads, manifests, coverage checks, and activation.
Fail-Closed Lowering gives claim-scoped failure outcomes.

**Exact remaining question.** I did not find an implemented runtime protocol that makes
shared-block activation atomic with request liveness, ownership, and scheduler admission.

**Research question.** Can provisional private blocks plus an epoch-fenced atomic page-table
install preserve recompute-equivalent output under connector faults, with under 3% overhead?

**Hypothesis.** A request-scoped activation barrier prevents visible partial state. Copy-on-
write prevents concurrent recovery from mutating blocks that another request can use.

**Strongest baseline.** Abort the request and perform full recomputation in fresh blocks.
Also compare with stop-and-copy staging.

**Cheapest experiment.** Reproduce one current vLLM failure. Add deterministic fault points
around lookup, transfer, activation, abort, sharing, and recomputation.

**Kill condition.** Kill the paper route if current main passes the matrix, or if fresh-block
full recomputation is correct and costs less than 3% at realistic fault rates.

**Biggest novelty threat.** Mooncake RFC 3692 describes most of the storage transaction.
Its prototype can expand to the runtime boundary before this thesis starts.

**Publication potential.** MEDIUM if failures span two connectors and the mechanism stays
small. LOW if it becomes one upstream bug fix.

**Product opportunity.** Build a connector conformance and fault-injection gate for vLLM,
SGLang, LMCache, Mooncake, and vendor KV tiers.

**Confidence that the public gap exists.** MEDIUM for the runtime boundary. LOW for a full
paper because current RFC work creates high scoop risk.

## 4.3 I-106 Per-layer KV reuse across adjacent policy updates

**Secret.** Adjacent RL checkpoints can change KV state unevenly by layer. Weight deltas
may identify a safe recomputation boundary.

**Problem.** A rolling policy update either drains sessions, keeps stale KV, or recomputes
the full prefix. The cost and quality trade-off are not measured for adjacent updates.

**Evidence.** KVShareArena tests cache reuse across checkpoints. It uses distant model pairs
and does not report adjacent-step layer drift. Mooncake's RL RFC states that stale KV can
be incorrect across weight versions.

**Closest prior work.** KVShareArena, ReKV, CacheBlend, PipelineRL, and Mooncake RL
disaggregation.

**What prior work already solves.** It establishes cross-checkpoint reuse evaluation,
cross-precision switching, partial KV recomputation, and version tagging.

**Exact remaining question.** Can weight delta alone predict the minimum KV layer suffix
that must be recomputed after one adjacent RL update?

**Research question.** Can a delta-based layer rule reduce update-time prefill work by at
least 30% while retaining at least 99% of full-recompute task quality?

**Hypothesis.** Drift concentrates in a subset of layers for small adjacent updates.

**Strongest baseline.** Full recomputation after each update. Also compare all-stale KV,
one fixed suffix boundary, and direct activation drift measurement.

**Cheapest experiment.** Use two adjacent OLMo-2 1B RLVR checkpoints on the Mac. Measure
per-layer K and V drift on 100 prompts before any serving implementation.

**Kill condition.** Kill if no fixed boundary saves 30% of layers at the stated quality,
or if weight-delta prediction performs no better than a fixed boundary.

**Biggest novelty threat.** KVShareArena introduced cross-checkpoint reuse in September.
An update can add adjacent checkpoints and per-layer analysis quickly.

**Publication potential.** LOW to MEDIUM. A positive result can support a narrow workshop
paper. A full systems paper needs a real online-update workload.

**Product opportunity.** Add cache-preserving rolling policy updates to RL serving systems.
The wedge is a version-aware drain and reuse controller.

**Confidence that the public gap exists.** LOW to MEDIUM. The exact measurement is absent
from the checked work. The workload need remains weak.

## 4.4 I-118 Power-coupled noisy neighbor on Grace superchips

**Secret.** A CPU tool job can reduce GPU prefill throughput without sharing CPU cores,
memory bandwidth, or GPU execution units.

**Problem.** Grace and the GPU share a module limit. CPU-side agent work can reduce the
power available to the GPU during compute-heavy prefill.

**Evidence.** NVIDIA documents the coupling and its CPU cap control. Existing GH200 work
measures power capping, but this review found no LLM-serving noisy-neighbor measurement.

**Closest prior work.** NVIDIA power steering, Dynamic Power Software, GH200 power-capping
studies, SuperInfer, and phase-aware LLM power control.

**What prior work already solves.** It provides power telemetry, cap controls, power
steering, and phase-aware GPU control.

**Exact remaining question.** Does CPU tool work cause material LLM prefill loss under a
documented module limit, and can a dynamic split beat the best static CPU cap?

**Research question.** Can phase-aware CPU capping improve mixed agent-serving goodput by
more than 5% over the best static cap without harming tool completion time?

**Hypothesis.** The effect appears in prefill and not in memory-bound decode.

**Strongest baseline.** The best static CPU power cap. Also compare NVIDIA automatic power
steering without intervention.

**Cheapest experiment.** Run the existing E-30 matrix for two hours on one GH200.

**Kill condition.** Kill if prefill changes by less than 3%, or if the best static cap is
within 5% of the oracle.

**Biggest novelty threat.** NVIDIA already exposes power steering. A reviewer can call the
result vendor tuning.

**Publication potential.** LOW. The likely result is a measurement note.

**Product opportunity.** Add superchip-aware cgroup and power controls to an agent platform.
This is likely a feature, not a company.

**Confidence that the public gap exists.** LOW. The exact LLM measurement seems absent.
The mechanism is documented and the oracle gap is probably small.

# 6. Best idea

I-23 remains the best first experiment. It is not yet a thesis commitment.

It wins for four reasons.

1. The oracle question is falsifiable before a large system exists.
2. One H100 can test the Hopper cells.
3. The existing harness reduces setup risk.
4. A negative result is useful. It can close the runtime-dispatch claim.

The novelty risk increased since R-05. FlashInfer-Bench now owns much of the system
surface. FlashInfer v0.7 owns production autotuning. The contribution must therefore be
the output-aware oracle and its resulting policy, not dynamic dispatch alone.

I-120 is the best backup. It has stronger direct failure evidence. However, Mooncake RFC
3692 creates a serious scoop risk. Start it only if the H100 reproduction still fails on
current vLLM and the runtime boundary remains open.

# 7. Exact first experiment

## 7.1 Question

Measure whether an output-aware contract changes kernel selection enough to beat a strong
per-shape allow-list.

## 7.2 Inputs

- Use one dense 7B to 9B model with native or supported FP8 execution.
- Use one MoE model that fits one H100 after FP8 quantization.
- Use 200 prompts from a public conversation or instruction dataset.
- Hold out 40% of prompts for policy evaluation.
- Add synthetic activation controls for zero, outlier, scale-boundary, and routing-skew cases.
- Pin vLLM, FlashInfer, CUDA, driver, model revisions, and container digest.

Do not add Blackwell NVFP4 to the first paid run. Add it only if Hopper passes the gate.

## 7.3 Workload

- Test prefill and decode separately.
- Sweep batch sizes 1, 2, 4, 8, 16, and 32.
- Sweep prompt buckets 128, 512, 2,048, and 8,192 tokens.
- Sweep MoE routing skew with real activations and controlled expert histograms.
- Test eager execution and CUDA Graph replay.
- Run exact greedy decoding for sequence comparisons.

## 7.4 Independent variables

- Kernel or backend.
- Model and layer family.
- Precision and scale rule.
- Batch size and prompt length.
- Prefill or decode phase.
- Routing skew.
- Eager or CUDA Graph execution.

## 7.5 Dependent variables

- Median and p95 kernel latency.
- End-to-end tokens per second, TTFT, and TPOT.
- Peak GPU memory.
- Maximum absolute, relative, and ULP error.
- Logit KL divergence and top-1 changes.
- Greedy first-divergence position and exact sequence agreement.
- Contract pass or fail.
- Policy overhead.

## 7.6 Baselines

1. Use the fastest kernel without output-aware checks.
2. Use the best single backend that passes all training cells.
3. Use fixed deterministic kernels where available.
4. Use FlashInfer autotuning with its reference correctness tests.
5. Use a per-shape output-qualified allow-list.
6. Use the offline fastest-safe oracle.

## 7.7 Procedure

1. Reproduce one known divergence. Stop if the harness cannot detect it.
2. Enumerate the available backend matrix from the pinned runtime.
3. Capture real layer inputs without changing their dtype or layout.
4. Run every candidate against one fixed reference implementation.
5. Record tensor, logit, sequence, performance, and memory results.
6. Build the per-shape allow-list on the 60% training prompts.
7. Compute the offline oracle on the 40% held-out prompts.
8. Fit no learned policy in the first run.
9. Test simple rules from phase, shape, scale statistics, and routing skew.
10. Bootstrap confidence intervals by prompt and repeat timing at least 30 times.
11. Run the chosen policies inside vLLM under closed-loop and open-loop load.
12. Apply the frozen decision rules.

## 7.8 Output files

- `configs/cells.yaml`: full matrix and exclusions.
- `manifests/runs.jsonl`: software, hardware, model, and seed data.
- `results/operator.parquet`: one row per operator cell and repeat.
- `results/sequence.parquet`: one row per prompt, backend, and regime.
- `results/policy.parquet`: oracle and baseline decisions.
- `results/decision.txt`: frozen GO, PIVOT, or KILL result.
- `plots/unsafe_by_regime.pdf`.
- `plots/speed_safety_frontier.pdf`.
- `plots/oracle_gap.pdf`.
- `plots/policy_overhead.pdf`.

## 7.9 Expected plots

1. Plot the speed and output-divergence Pareto frontier by regime.
2. Plot backend winners across phase, batch, length, and routing skew.
3. Plot oracle gain over the per-shape allow-list.
4. Plot unsafe substitution rate against tensor tolerance.
5. Plot end-to-end gain after policy overhead.

## 7.10 Interpretation

**FACT after the run.** Report only measured cells and confidence intervals.

**INTERPRETATION.** A changing winner is useful only if the held-out policy captures it.

**HYPOTHESIS.** MoE routing skew and graph mode create the largest safe-winner changes.

**PROPOSED CONTRIBUTION.** Add output-aware qualification to the autotuning decision.

## 7.11 GO, PIVOT, and KILL criteria

These thresholds are project heuristics.

**GO.** Require at least 5% oracle gain on two models. Also require a simple held-out
policy to beat the per-shape allow-list by at least 2% with zero contract violations.

**PIVOT.** Use a measurement paper if oracle gain is below 5%, but at least 10% of default
substitutions violate the sequence contract.

**KILL.** Kill the runtime-dispatch thesis if gain is below 2% on every model and the
unsafe fraction is below 2%.

**KILL.** Also kill if FlashInfer's existing reference checks and per-shape allow-list
capture at least 95% of oracle gain.

## 7.12 Compute tiers

- No GPU: validate manifests, analysis code, and decision scripts.
- One H100: run the complete Hopper gate.
- One B200: add NVFP4 only after the Hopper gate passes.
- Multiple GPUs: not required for the first claim.
- Real cluster: not required for the first claim.
