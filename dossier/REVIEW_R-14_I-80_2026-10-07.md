## 2. Prior art (closest 5, plus others)

1. CONCUR, arXiv 2601.22705, 2026-01-30, checked (abstract). FACT: it is a control layer that regulates agent admission from runtime cache signals. It targets "middle-phase thrashing". It reports up to 4.09x on Qwen3-32B and 1.90x on DeepSeek-V3. It is batch inference. The page does not mention timeouts or retries. It also appears as PACE (ICML 2026 poster, search-only). It does NOT cover online arrivals, spikes, or client retries. It DOES cover the fix that my simulator shows is enough.
2. Service-Induced Congestion in Memory-Constrained LLM Serving, arXiv 2606.15555, 2026-06-14, checked (abstract). FACT: memory cannot be overcommitted. Eviction and recompute make the service create its own congestion. Eviction-free equilibria can be unstable. It derives an admission cap (the search snippet says it uses the eviction-free rate x* as a per-iteration cap; search-only). It does not use the word "metastable". It does not cover retries or prefix caching. This is the strongest threat to novelty of the premise.
3. Continuum, arXiv 2511.02230, 2025-11-04 (v7 2026-09-08), checked (abstract). FACT: it pins the KV cache with a TTL after a tool call. It uses program-level FCFS. The abstract does not mention retries or admission. It covers "protect admitted sessions from eviction". It does not cover load shedding.
4. CacheWise, arXiv 2606.16824, checked (abstract). FACT: reuse-aware eviction for coding agents using tool-call metadata. The abstract does not mention admission or retries.
5. LUMEN, arXiv 2606.17787, 2026-06-16, checked (abstract). FACT: load-aware recovery after a worker failure. The abstract does not mention retries, admission, or metastability. INTERPRETATION: it covers the "lost cache plus lost capacity" trigger, not the retry loop.

Others:

## 3. First principles

Client timeouts. FACT (checked, openai-python README): the default timeout is 10 minutes and max_retries is 2. Timeouts are retried. The Anthropic SDK defaults are about the same (not checked on a primary page, from the SDK page that I fetched it gave only my memory). INTERPRETATION: with a 600 s timeout, a retry needs a request to wait 10 minutes. That happens only after a long overload. A tuned agent harness may use 30 to 120 s. A gateway may time out earlier. So the retry loop depends on a setting that operators control. It is not a default behavior.

Retry re-sends the same prompt. INTERPRETATION: the client sends the same tokens whether the cache was evicted or not. Only server prefill changes. So "retry amplification" is really "miss amplification". Retries add a second effect: duplicate admission of a request whose first attempt is cancelled.

Amplification. Assumptions (INTERPRETATION, not measured): 8B model, H100, prefill 20k tokens/s, decode step about 17 ms at batch 19. KV per token for Llama-3-8B is 131,072 bytes (computed: 2 x 32 layers x 8 KV heads x 128 x 2 bytes). A 300k-token cache is about 39 GB. A turn with a cache hit prefills 800 tokens (0.04 s) and decodes 250 tokens (about 0.22 s GPU share). A turn with a full miss at 16k context prefills 0.8 s. So GPU time per turn is about 0.26 s on a hit and about 1.0 s on a miss. That is about 4x. The memory limit matters more: 300k tokens hold only about 19 sessions of 16k tokens. So the good state needs the active-session working set to fit in the cache.

Is a lasting collapse possible? FACT (my simulator, section 5): yes, in a window of load. The cause is the working set, not retries.

## 4. Is the fix trivial?

FACT (simulator, 4 seeds, lambda 0.09 and 0.11 sessions/s, 4x spike for 60 s):
- FIFO + LRU + recompute preemption ("none"): tail goodput 0.62 to 0.82 turns/s against 1.34 to 1.60 before the spike.
- Lower max_num_seqs (16): tail 0.64 to 1.03. Partial.
- Waiting-queue cap with rejection (8 or 32): no fix (0.67 to 0.83).
- Retries=0: tail the same as with retries (0.72 vs 0.62; 0.82 vs 0.82; 0.77 vs 0.77).
- Session-concurrency cap at 16 to 20 with gateway queueing: tail 1.20 to 1.70. No collapse, no timeouts, no preemptions.

INTERPRETATION: a one-line cap on active sessions, sized as cache tokens divided by mean context, removes the collapse. That cap is Denning's working-set control (I-61) and CONCUR. The remaining question is how to size the cap online. That is CONCUR's contribution for batch. Cap sizing is sensitive: cap 12 lost 15 percent of pre-spike goodput, cap 24 started to preempt again (about 450 to 480 preemptions per run).

## 5. Simulator run (premise check done early)

Files: scratchpad/r14/sim.py, cal.py, g1.py, g2.py, g3.py (pure Python 3, a few minutes in total).

Model (FACT, as coded): one replica; iteration-level steps; step time = 0.015 s + 0.0001 s x decode seqs + 5e-5 s x prefill tokens (that is 20k tok/s); chunked prefill budget 4096 tokens; max 64 seqs; KV capacity 300k tokens; LRU eviction of idle-session caches by tail trimming; recompute preemption of the newest running request (tokens decoded so far are folded into the prompt); sessions: 8k initial context, +800 tool tokens and 250 output tokens per turn, 15 turns, tool gap lognormal (median 4 s, sigma 1); open Poisson session arrivals; spike at t=300 s for 60 s; client timeout T, 2 retries, backoff 1 s x 2^k with jitter; server cancels a timed-out request and keeps the computed prefix.

Results (FACT, 4 seeds, mean):
- Good-state capacity: about 1.8 turns/s (cap 20). Bad-state throughput: about 0.8 to 1.0 turns/s. Window of offered load with bistability: about 1.0 to 1.8 turns/s (0.07 to 0.12 sessions/s). Above the window the system collapses with no spike at all (plain overload). Below it the system recovers.
- A spike of 2x for 30 s at 0.09 sessions/s (75 percent of good capacity) leaves tail goodput 0.84 against 1.34 before. A 3x/30 s spike left 1.10. A 8x/15 s spike left 1.11. Results are noisy.
- T=600 s (no retry ever fires) still collapses: tail 0.76 to 0.86 at 0.09 to 0.11 sessions/s with 4x spike. T=60 s is a little worse in some cells and adds timeouts and session failures.
- Cache size scaling (C=600k, lambda doubled): pre 2.50, tail 1.08.
- No spike is needed above the window. So "metastable" holds only inside the window.

Not modelled (limits, INTERPRETATION): cross-session shared prefix (system prompt and tool schema, which would shrink the working set; my sessions each hold an unshared 8k prefix, so the model is pessimistic); multiple replicas and routing; real vLLM scheduler details (watermarks, block size, swap); hardware constants are my assumptions and are not calibrated on a real GPU; short horizon and 4 seeds; goodput windows of 30 s are noisy; closed-loop session arrival (agents that wait for load to drop) is not modelled; zombie work after client disconnect is not modelled (HYPOTHESIS: it makes retries worse; vLLM behavior on disconnect was not checked).

## 6. Visible gain

INTERPRETATION: against "none", a cap gives about 1.6x to 2.2x tail goodput (FACT in my model). Against the best simple baseline (a tuned session cap), a cache-aware extra (pin admitted caches, shed evicted sessions first) has little room. With the cap at 20 the preemption count is near zero, so pinning has nothing to protect. HYPOTHESIS: a gain above 15 to 20 percent over a tuned cap exists only when the cap is mis-sized or the context length varies widely. That is a tuning result, not a mechanism transfer.

## 7. Combinations

- I-80 + I-61. Job split: Denning cap bounds active sessions to the cache; a pinning or TTL (Continuum) protects admitted sessions. This is the effective fix. It is not novel: CONCUR, 2606.15555 and Continuum cover its parts. Verdict WEAK. The only open gap is "online, with spikes and timeouts". Is that a thesis? No: it would be a measurement plus a known fix.
- I-80 + I-74. Job split: idempotency stops duplicate work after a timeout. My run shows retries=0 changes tail goodput by at most 0.1 turns/s. Verdict KILL.
- I-80 + I-59. Priority inheritance fixes a high-priority request that waits on a shared-prefix producer. It does not touch session working-set thrash. A combination would be two unrelated tricks. Verdict KILL.
- I-80 + I-60. Late binding with a locality timeout is a router. A session cap could use late binding to pick a replica with cache room. HYPOTHESIS only; nothing in my run tests it. Single-replica collapse remains unchanged. Verdict WEAK.

## 8. Recommendation for E-28

Do not run E-28 as written ("KILL if no collapse"). My run already answers it: a collapse exists, but the retry story fails and the fix is known. Change the question before spending more time.

If the user still wants the topic, the only narrowed claim worth a test is: "At a given load, an online adaptive session cap that uses only server signals (preemption rate, hit rate) matches the best static cap within 10 percent across changes in context length and tool-gap distribution, while static caps lose more than 20 percent." That is an adaptive-control claim. CONCUR already does a version for batch. HYPOTHESIS: this is thin for a thesis.

Heuristic thresholds (labelled heuristics, not derived):
- KILL if a static session cap tuned per setting keeps tail goodput within 10 percent of the best adaptive policy over a sweep of context length (4k to 32k), tool gap (1 to 30 s), and cache size.
- KILL if retries=0 gives tail goodput within 10 percent of retries=2 (this already holds in the current run).
- PIVOT if the collapse needs load inside a window narrower than 20 percent of capacity. (In my run the window is wide, 1.0 to 1.8 turns/s, so this does not trigger.)
- GO only if an adaptive policy beats the best tuned static cap by more than 20 percent in at least 3 of 5 workload mixes, and with shared prefixes in the model.

Baselines E-28 must include: (1) FIFO + LRU + recompute (vLLM default); (2) lower max_num_seqs; (3) waiting-queue cap with 503; (4) token-bucket or retry budget at the client; (5) static session cap sized from cache / mean context, with sweep; (6) Continuum-style TTL pinning; (7) CONCUR-style adaptive cap (re-implemented); (8) the oracle best static cap per scenario.

Simulator must add before it is credible: shared system-prompt prefix across sessions; block-granular paged KV with watermarks; real step-time model fitted to a published vLLM profile (not a guess); closed-loop clients; zombie work on disconnect; mixed load with non-agent requests; 10+ seeds with confidence intervals.

## 9. Verdict reasons (three strongest)

1. The retry claim fails: collapse persists with no retries (T=600 s) and with retries=0 gives the same tail goodput as retries=2.
2. A session cap sized to the cache fixes the collapse. A queue cap does not. The effective fix is Denning's working-set control, already published as CONCUR and 2606.15555.
3. Collapse is real but needs offered load in a bistable window. Above the window, plain overload collapses without a spike. Below it, the system recovers.
