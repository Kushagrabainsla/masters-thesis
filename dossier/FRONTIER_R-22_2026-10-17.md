# Frontier Systems Review R-22

Date: 2026-10-17

Scope: Continue R-21 until three total new public gaps survive. Count I-120 from R-21.

Status: Literature review and experiment design. No experiment ran. No thesis direction is chosen.

## Method and limits

This review used two literature passes.

Pass 1 mapped nine transitions in current systems and generated eight new candidate truths.
It checked papers, official documentation, repositories, issues, RFCs, and production guides.

Pass 2 searched each narrow mechanism by synonyms. It attacked exact work, adjacent domains,
simple baselines, scale, oracle value, feasibility, and current roadmaps.

The review stopped when three total gaps survived: I-120 from R-21, I-122, and I-123.
This stopping rule follows the user's instruction on 2026-10-17.

The review did not reproduce GPU results. Public-gap confidence is not proof of novelty.

# 1. What changed in the world?

## 1.1 Input can change while inference is active

**FACT.** vLLM now supports resumable streaming-input sessions. A client can append input
to a live request instead of starting an independent request.

**FACT.** vLLM issue 49449 changes a live token sequence during a session rebuild. The
runtime retains an old block hash. A later request reuses the wrong KV state and changes
deterministic output.

**FACT.** vLLM issue 58776 shows that one counter represented two different facts. It
represented materialized KV positions and valid token history. Preemption made them differ.

**FACT.** vLLM issue 36755 reports an async scheduling race. Output processing reads a
live mutable request after the next schedule step changes it.

**INTERPRETATION.** Append-only request state is no longer a safe internal assumption.
The system needs a commit boundary for a version of the whole session.

## 1.2 Real-time models retain heterogeneous state

**FACT.** The vLLM-Omni streaming ASR RFC identifies frontend continuity, convolution
tails, acoustic context, predictor recurrence, and output progress as one coherent state.

**FACT.** An RNN-T frame can emit zero or several labels. Token position cannot identify
the acoustic state boundary.

**FACT.** The RFC prohibits recompute preemption for its first version. Tokens cannot
reconstruct the acoustic state. It lists complete-session offload and migration as later work.

**FACT.** The vLLM-Omni real-time video roadmap also leaves migration, recovery, and
offload for a later phase.

**INTERPRETATION.** KV-only recovery is insufficient for real-time speech and world models.
Recovery must include opaque model state and the external input and output frontiers.

## 1.3 Complete execution-state snapshots became practical

**FACT.** Execution-State Capsules snapshots KV, recurrent, convolution, MTP, and metadata
state. It reports sub-millisecond GPU-resident restore on an RTX 5090.

**FACT.** It reports 3.9 to 27 times TTFT speedup over cold prefill from 2K to 16K tokens.
Its evaluated scope is one device and small-batch physical-AI serving.

**INTERPRETATION.** Complete state capture is technically plausible. The open question is
whether a consistent distributed recovery cut can meet real-time overhead and latency limits.

## 1.4 Asynchrony creates tentative state

**FACT.** vLLM issues 54260, 52071, and 49355 report failures when speculative decoding,
pipeline parallelism, and async scheduling interact.

**FACT.** LLM-42 implements verified speculation and rollback for deterministic inference.

**FACT.** ONNX Runtime GenAI documents buffered speculative output and interrupted-round
reconciliation. A 2026 transactional KV preprint separates committed KV from speculative KV.

**INTERPRETATION.** The commit-frontier problem is real. It is not a new standalone gap.

## 1.5 New model classes invalidate autoregressive batching rules

**FACT.** One H200 characterization of masked diffusion LLMs reports 11 discrete step
levels. Its best admission-time predictor has R-squared 0.150.

**FACT.** Only 24% of single-request wall time is GPU computation in that setup. A shared
batch of 16 improves throughput 16 times over per-request dispatch.

**FACT.** vLLM-Omni already has step-wise continuous batching. Each request advances
independently and keeps separate progress, random state, cancellation, and errors.

**INTERPRETATION.** The transition is important. The obvious slot-batching mechanism is
already implemented.

## 1.6 Cancellation became distributed resource reclamation

**FACT.** llm-d documents a vLLM P-side KV stranding window that was 480 seconds under
the original NIXL timeout design. NIXL-backed SGLang can retain P-side KV until restart.

**FACT.** Current vLLM documents lease renewal for this exact problem. The SGLang Q4
roadmap lists generation-tagged ABORT and ABORT_ACK handling.

**INTERPRETATION.** Cancellation correctness is important. Current projects already own
the direct protocol work.

# 3. Ideas killed by prior work

## 3.1 I-124 Authoritative commit frontier for tentative tokens

**Exact-work attack.** LLM-42 implements verified speculation and rollback. ONNX Runtime
GenAI separates buffered speculative output from committed output.

**Different-name attack.** Transactional KV caching separates stable and speculative KV.

**Baseline attack.** Disable async scheduling or buffer output until verification commits.

**Verdict.** KILL as a separate thesis. Use its invariant inside I-122.

## 3.2 I-125 Elastic slot batching for masked diffusion LLMs

**Exact-work attack.** vLLM-Omni's `StepScheduler` advances requests independently within
continuous batches. Its tests include partial completion and cancellation.

**Scoop-risk attack.** The H200 characterization paper explicitly proposes slot batching.

**Verdict.** KILL. The open work is policy tuning inside an existing mechanism.

## 3.3 I-126 Cancellation-debt scheduling for agent branch races

**Relevance attack.** Speculative agent systems create work that can be discarded.
However, no public production trace establishes cancellation rate as the dominant cost.

**Exact-work attack.** vLLM uses renewable P-side KV leases. SGLang's roadmap has
generation-tagged abort acknowledgements and deferred release.

**Adjacent-work attack.** TAPER regulates parallel branch admission before excess work starts.

**Verdict.** KILL as a new route. Reopen after a cancellation-heavy trace shows a policy gap.

## 3.4 I-127 Online isolation for generated GPU kernels

**Exact-work attack.** M2K uses model-aware symbolic execution and reports hundreds of
previously unknown CUDA memory bugs. It is accepted to SOSP 2026.

**Adjacent-work attack.** KREX provides concurrent kernel benchmarking on shared GPUs.
CUDA process contexts already provide an ordinary fault boundary.

**Combination attack.** A subprocess around M2K and KREX is integration work.

**Verdict.** KILL as new research. Keep it as motivation for I-23 qualification.

## 3.5 I-128 Topology-independent data-loader recovery

**Exact-work attack.** Mosaic Streaming supports deterministic mid-epoch resumption across
24 to 16 to 48 GPUs, if the global batch size stays constant and divisible.

**Adjacent-work attack.** Megatron and Cerebras save data-stream positions.

**Verdict.** KILL. The general mechanism already exists.

## 3.6 I-129 Adaptive recurrent-state checkpoints for hybrid models

**Exact-work attack.** Sparse Prefix Caching optimizes checkpoint placement. Tail-Replay,
SuffixReplay, HYPIC, and DASC address recurrent-state reuse directly.

**Repository attack.** vLLM RFC 52959 adds internal Mamba checkpoints.

**Verdict.** KILL. This also confirms the older I-95 verdict.

## 3.7 I-130 Compiler and CUDA-graph warm state in training checkpoints

**Exact-work attack.** PyTorch Mega-Cache exports portable compiler artifacts. Foundry
materializes CUDA graph contexts and cuts a reported 10-minute startup to 3.9 seconds.

**Baseline attack.** A shared compiler cache plus ordinary graph recapture may remove most
restart cost. The remaining training-specific premise is not measured.

**Verdict.** KILL as a thesis route. Reopen only with a real training recovery breakdown.

# 4. Surviving ideas

## 4.1 I-120 Atomic runtime activation for remote KV recovery

**Secret.** A remote KV hit is a transaction. It is not a collection of independent block loads.

**Problem.** Correct remote objects can become wrong runtime state after partial activation,
sharing, abort, or concurrent recomputation.

**Evidence.** vLLM issue 49250 reports deterministic wrong output after a rejected load.
LMCache issues report partial-retrieve crashes and long waits.

**Closest prior work.** Mooncake Store, Mooncake RFC 3692, Fail-Closed Lowering, LMCache,
and vLLM recovery paths.

**What prior work already solves.** It solves storage consistency, transfer, manifests,
coverage checks, and some failure outcomes.

**Exact remaining question.** Can a runtime activate all required state with one fenced
publish step tied to request ownership and scheduler liveness?

**Research question.** Can private provisional blocks and epoch-fenced activation preserve
recompute-equivalent output under connector faults, with less than 3% overhead?

**Hypothesis.** The protocol prevents partial visibility. Normal execution pays only
metadata and one publish operation.

**Strongest baseline.** Fail closed, discard all loaded blocks, and recompute into fresh blocks.

**Cheapest experiment.** Reproduce vLLM issue 49250. Then inject failures around lookup,
transfer, activation, sharing, abort, and recomputation.

**Kill condition.** Kill if current main passes the matrix. Also kill if fresh-block
recomputation costs less than 3% at realistic failure rates.

**Biggest novelty threat.** Mooncake RFC 3692 proposes activation. The scoop risk is very high.

**Publication potential.** MEDIUM only if the runtime invariant spans two connectors or engines.

**Product opportunity.** Add a correctness proxy and conformance suite for external KV stores.

**Confidence that the public gap exists.** MEDIUM at the runtime boundary.

## 4.2 I-122 Versioned commit for mutable real-time sessions

**Secret.** A live inference session is a versioned object. It is not an append-only request.

**Problem.** Streaming updates can change token history while queued work, block hashes,
materialized KV, parser state, and emitted output refer to an older history.

**Evidence.** vLLM issue 49449 produces deterministic wrong output from a stale hash.
Issues 58776 and 36755 show state aliasing across preemption and async steps. Issue 42655
shows stale batch-row identity after repeated streaming updates.

**Closest prior work.** vLLM resumable sessions, vLLM session-identity RFCs, LLM-42,
ONNX Runtime speculative decoding, and MVCC in databases.

**What prior work already solves.** vLLM supports updates and session identity. Speculative
decoders buffer tentative tokens. Databases provide version and publish patterns.

**Exact remaining question.** I did not find a public runtime that commits one immutable
session version across token history, cache identity, materialized-state extent, queued work,
parser state, and emitted output.

**Research question.** Can generation-tagged copy-on-write session versions remove
streaming-update races with less than 2% throughput cost versus current in-place mutation?

**Hypothesis.** One schedule-time version and one token-boundary publish remove the known
stale-state interleavings. Metadata cost remains small.

**Strongest baseline.** Abort the request, allocate a new cache namespace, and fully re-prefill.
Also compare with simple hash invalidation and synchronous scheduling.

**Cheapest experiment.** Build a CPU state-machine harness around vLLM scheduler tests.
Enumerate update, replace, cancel, preempt, stop, speculative, and parser-flush interleavings.

**Kill condition.** Kill if full abort and rebuild costs less than 3% in realistic update
traces. Kill if current main passes the matrix and simple invalidation fixes every failure.

**Biggest novelty threat.** vLLM fixes these issues quickly. The work becomes a bug patch
unless one protocol covers at least two independent state consumers.

**Publication potential.** MEDIUM for a cross-component protocol and model checker.
LOW for one vLLM patch.

**Product opportunity.** Add a conformance and fault-injection layer for real-time model APIs.

**Confidence that the public gap exists.** MEDIUM. The failures are public. The field moves quickly.

## 4.3 I-123 Commit-indexed recovery for heterogeneous real-time session state

**Secret.** Real-time model recovery needs an application-consistent stream cut. A GPU
memory snapshot alone is not a session checkpoint.

**Problem.** Speech and world-model sessions combine opaque model state, pending input,
emitted output, playback progress, controls, and ownership. A crash can restore mutually
inconsistent frontiers or repeat an external output.

**Evidence.** The vLLM-Omni ASR RFC says tokens cannot reconstruct acoustic state. It
requires coherent state updates and lists whole-session migration as follow-up work.
The real-time video roadmap also leaves recovery and migration open.

**Closest prior work.** Execution-State Capsules, vLLM-Omni persistent state, WorldMove,
DéjàVu, Llumnix, and classic stream-processing checkpoints.

**What prior work already solves.** Capsules capture complete device state on one GPU.
WorldMove migrates world-model cache. DéjàVu replicates KV. Stream processors align logs
and state at checkpoints.

**Exact remaining question.** I did not find public work that recovers an active real-time
model session from a commit index spanning opaque model state, input receipt, output emission,
and client acknowledgement.

**Research question.** Can periodic complete-state snapshots plus an input log and an
output commit index recover a real-time session within 200 ms, with less than 10% steady-state
overhead and no duplicate committed events?

The 200 ms and 10% thresholds are project heuristics. They are not literature standards.

**Hypothesis.** Fixed-size recurrent state makes incremental snapshots small. Input replay
closes the gap between the last snapshot and the acknowledged commit frontier.

**Strongest baseline.** Restart the session and replay all retained input. Also compare
with synchronous full-state replication after every chunk.

**Cheapest experiment.** Use a CPU state-machine simulator first. Sweep state size, chunk
rate, snapshot bandwidth, failure time, and acknowledgement delay. Then measure one model
on one GPU with same-GPU process restart.

**Kill condition.** Kill if per-chunk full replication stays below 3% overhead. Kill if
replay from the last committed input already meets 200 ms. Kill if opaque state cannot be
restored exactly through current model interfaces.

**Biggest novelty threat.** Execution-State Capsules already captures complete state.
vLLM-Omni roadmaps name migration and recovery explicitly. Scoop risk is high.

**Publication potential.** MEDIUM if the consistent-cut protocol works across speech and
one world model. LOW if it only serializes one model's tensors.

**Product opportunity.** Provide high-availability session hosting for voice agents and
interactive world models. The first wedge is a recovery library for vLLM-Omni plugins.

**Confidence that the public gap exists.** MEDIUM to LOW. The narrow question is open in
the checked work, but public roadmaps point directly at it.

# 6. Best idea

I-122 is the best new CPU-first idea from this pass.

I-120 has stronger direct evidence, but its cheapest decisive test needs a current connector
and one NVIDIA GPU. Mooncake RFC 3692 also creates a direct scoop risk.

I-122 has three advantages. The known failures reproduce at scheduler level. A CPU harness
can test most interleavings. The protocol applies to cache, scheduler, and parser state.

I-123 is important, but its premise can fail cheaply. Complete state might be small enough
that synchronous replication is sufficient. Run its oracle before any runtime implementation.

This ranking does not replace I-23 as the best planned first H100 experiment.

# 7. Exact first experiment

## I-122 CPU state-machine and trace-replay gate

### Inputs

- A pinned current vLLM commit.
- Scheduler-level request objects and mock model outputs.
- Reproducers from issues 49449, 58776, 36755, 42655, and 51697.
- Synthetic session traces with 1, 10, 100, and 1,000 concurrent sessions.

### Workload

Generate session operations with these event types:

- append input;
- replace an uncommitted suffix;
- schedule a step;
- complete an old step;
- preempt;
- cancel;
- accept zero, some, or all speculative tokens;
- observe a stop token;
- flush a tool parser;
- disconnect and resume.

Use deterministic seeds. Record every operation and version.

### Independent variables

- session count: 1, 10, 100, 1,000;
- outstanding schedule depth: 1, 2, 4;
- update probability: 0%, 1%, 5%, 20%;
- preemption probability: 0%, 1%, 10%;
- speculative width: 1, 4, 8;
- cache block size: 8, 16, 32 tokens;
- parser mode: text only or tool-call streaming.

### Dependent variables

- invariant violations;
- wrong cache-key publications;
- stale output applications;
- duplicate or omitted emitted events;
- orphaned requests or blocks;
- metadata bytes per session;
- scheduler operations per token;
- end-to-end CPU throughput in the harness.

### Baselines

1. Current pinned vLLM behavior.
2. Full abort, new namespace, and complete rebuild.
3. Hash invalidation only.
4. Synchronous scheduling with streaming updates.
5. Proposed generation-tagged immutable session versions.

### Procedure

1. Freeze the state schema and invariants before implementation.
2. Reproduce every source issue with the current baseline.
3. Add a reference sequential interpreter with no overlapping steps.
4. Generate valid concurrent histories.
5. Compare every committed version with the sequential interpreter.
6. Shrink failing histories to minimal counterexamples.
7. Run the scale sweep for all baselines.
8. Run a different-model pre-run review before any GPU validation, as D-29 requires.
9. If the CPU gate passes, run one small model on one NVIDIA GPU.

### Output files

- `manifest.json` with commits, versions, seeds, and parameters;
- `histories.jsonl` with operation histories;
- `violations.jsonl` with minimized counterexamples;
- `summary.csv` with correctness and cost metrics;
- `throughput.csv` with the scale sweep;
- `plot_violations_by_interleaving.pdf`;
- `plot_overhead_vs_concurrency.pdf`;
- `README.md` with exact reproduction commands.

### Expected plots

- Violations by interleaving class and baseline.
- Throughput overhead versus concurrent sessions.
- Metadata memory versus concurrent sessions.
- Rebuild cost versus update position and context length.

### Interpretation

**GO.** The current engine or simple invalidation fails valid histories. The proposed
protocol removes all failures. CPU overhead stays below 2% at 1,000 sessions.

**PIVOT.** The problem is real, but immutable versions cost more than 2%. Reduce the
protocol to schedule-time snapshots or a smaller commit record.

**KILL.** Current main passes the complete matrix. Also kill if hash invalidation fixes
all failures, or full abort and rebuild adds less than 3% under realistic update rates.

All numeric thresholds are project heuristics.
